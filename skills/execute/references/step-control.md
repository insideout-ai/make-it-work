# Durable step control

For a controller-enabled implement run, use `<execute-base>/scripts/step-control.mjs` as the required boundary for dispatch, fix attempts, and completion. Standalone/legacy plans retain their existing Progress behavior unless explicitly opting into this helper. Its journal is `<plan-path>.execution.json`, bound to plan content excluding Execution Status. A replan uses its new plan path; do not erase a stopped/changed journal to bypass a guardrail or retry cap.

After completing a step when the saved Inline policy requires user review, the main session must checkpoint `await-input` with `kind: step` under [the pending-input contract](../../implement/references/controller.md#pending-input-lifecycle) before pausing. The default choice IDs are `continue` and `stop`: Continue resumes the same Execute phase; Stop checkpoints Stopped. Neither changes Progress or evidence. Execution-mode/backfill/verification questions use the same lifecycle. Autopilot's documented no-pause policy still applies; do not create a new interactive wait for an automatic default.

Before dispatch, run `inspect --plan <plan> --ledger <verification-path> --ticket <ticket> --plan-version <n>`. It returns the next eligible step, verified completion count, any recorded `active_steps`/`active_dispatch`/`started_at`, and checks evidence for already-complete steps. A recorded start is not proof that an agent process is still alive: on resume reconcile the existing agent/result before redispatch. Reusing the start event repairs a checkpoint; it never authorizes launching a duplicate agent. Dependency references and consecutive numbering are validated. For concurrent fix rounds call the exported `executionControl` inspect with `parallel: true` (or place `{ "action": "inspect", "parallel": true }` in an event input). Only mutually marked, contiguous, dependency-ready steps with disjoint declared files form a batch; semantic independence remains a planning obligation.

For mutations run `step-control.mjs apply --plan <plan> --input <event.json> --ledger <verification-path> --ticket <ticket> --plan-version <n> [--dashboard-state <state>]`:

- Immediately before launching a step's agent or starting its Inline work: `{ "action": "start", "id": "step-4-dispatch-1", "steps": [4] }`. A real parallel batch records all member numbers in one start event before launching any member. Supply the existing dashboard state path when participating. The helper validates eligibility, records the active step/batch and its start time, and refreshes the HTML with the plan titles and verified count before returning. Starting does not change Progress, verification evidence or fix-attempt counts. A failed command blocks dispatch. Retry the identical event ID to recover the checkpoint; do not create a second start while work is already active. Earlier journals without start metadata remain readable; adopt an already-running unfinished step only after reconciling its actual agent state, without repeating its work.
- Before each code-fix attempt to make a failing check pass: `{ "action": "begin-attempt", "id": "step-1-fix-1", "step": 1 }`. Reuse the ID only when retrying the same checkpoint call; a new actual fix uses a new ID. For a member of an eligible concurrent batch add `parallel: true`. Count implementation attempts, not every test invocation or initial baseline check. A sixth attempt is refused across invocations.
- On guardrail or exhaustion: `{ "action": "stop", "reason": "guardrail" }` or `retry-limit`. Persist this before returning the fixed stop report. A stopped journal permits no later dispatch or completion.
- On terminal agent/tool failure after a recorded start: `{ "action": "stop", "reason": "execution-failed", "detail": "<concise observed failure>" }`, then return the existing `EXECUTE_STOPPED` outcome with the actual error. Ordinary failed checks being retried are not terminal stops. Stop checkpoints clear the running display and update activity without claiming completion. The parent still checkpoints the workflow's Stopped state; do not invent verification evidence or a new handoff outcome.
- A fresh invocation after explicit user guidance may use `{ "action": "resolve-stop", "source": "user", "via": "chat", "reason": "<actual guidance>" }`. It retains stop/attempt history and starts a new attempt budget; edited unfinished steps may be rebound only if already-complete steps are unchanged. Autonomy/defaults never resolve a correctness stop. A replan instead uses its new plan-version path.
- After actual Verify and named checks pass: `{ "action": "complete", "steps": [{ "number": 1, "checks": [...] }] }`. Checks use the existing verification schema (`type`, `subject`, `command`, `result`, `note`). Supply every member together for a real batch, only after all returned. One failed member means do not call completion; leave ledger and Progress unchanged and record the stop. Participating controller runs require the exact started step/batch. The helper validates/persists evidence, clears the running state, then calls plan-status to advance Progress and refresh the dashboard with the verified count and readiness for the next step/gate. Subagents return actual checks; the orchestrator alone runs this completion command. Do not also write the ledger or call complete-step/complete-batch directly.

Repeat an identical completion event after a dashboard failure; its receipt validates saved evidence and recovers without duplicate Progress. Any command failure prevents the next dispatch. Changed plan content requires resolving/replanning through implement; the helper never guesses which prior evidence remains valid. Manual observations and semantic test adequacy are not proved by a JSON validator.

An append-only fix amendment retains prior step evidence but clears the old completion gate. The amended plan must run its gate again before a terminal passing handoff. New AC traceability rows begin unverified; a change to prior traceability is a reassessment blocker.
