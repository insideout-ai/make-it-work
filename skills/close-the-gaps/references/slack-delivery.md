### Phase 5D — Slack Export

Prepare a draft or send the questions to the ticket's Product Manager according to the user's choice, then stop. Both modes write the questions file and pause without polling Slack; Phase 5C reads the PM's answers from the Slack thread on resume. Sending requires an explicit `Send via Slack` choice, `--slack-send`, or Phase 5E's `Pause and send to Product` selection with supported sending disclosed; draft mode and a legacy generic Slack choice never permit sending.

1. **Build the question list** exactly as Phase 5B steps 1–2 do — every wave, conditional follow-ups labeled with the answer they depend on, and any `## Follow-up Needed After This Round` items. For a partial-answer handoff from Phase 5E, preserve resolved answers in the file and include only unresolved questions and applicable conditional follow-ups in the message, with answered decisions as context. Do not call `AskUserQuestion` for the questions themselves.
2. **Identify the Product Manager.** Honor an explicit recipient supplied by the user; otherwise resolve the ticket's PM before looking them up in Slack:
   - **Jira custom-field discovery:** Product Manager is a custom field; Reporter is the built-in `reporter` field. Use field metadata/name mappings returned by Jira, or the connector's field-discovery/search capability, to resolve the field named **Product Manager** to its actual `customfield_<id>` key for the ticket's Jira site/project. Read that key's value from the issue; request it explicitly if the initial issue response omitted custom fields. Do not assume a built-in `productManager` property, guess an ID, or reuse an ID from another Jira site.
   - **Precedence and fallback:** use the populated Product Manager custom field first. Use Reporter only when the PM field is confirmed absent or empty, and identify this as a Reporter fallback when showing the recipient. A field omitted from a response, failed discovery, inaccessible metadata, or multiple unresolved matching fields is not proof that the PM field is empty. In those cases ask the user to identify the PM rather than silently substituting Reporter. For other trackers or pasted tickets, use their explicitly supplied PM, otherwise their reporter when available.
   - Look the resolved person up via the Slack MCP integration. Show the matched Slack user (name and handle), state whether they came from the PM field or Reporter fallback, and ask the user to confirm or name a different person. If no person or Slack match can be resolved, ask who the PM is. (autopilot: accept an unambiguously derived recipient without confirmation; unresolved custom-field discovery or recipient matching falls back to Phase 5B with the reason, without guessing.)
3. **Compose and show the message** with the confirmed recipient, using this welcoming template. Replace the placeholders and render the ticket title as a clickable link using the Slack tool's supported formatting. The initial send choice already authorizes delivery; this preview does not introduce another confirmation gate.

   ```text
   close-the-gaps — <TICKET-or-slug>: <ticket summary>

   Hey <PM first name> 👋

   We're getting <ticket-url|TICKET-or-slug — ticket summary> ready for development, and your input would help clear up a few details.

   <Numbered questions and answer options>

   Please reply in this thread, one reply per question—for example, Q2: B. Feel free to add context or suggest a different answer! For open-ended questions, start with the question number and write your answer in your own words.

   Thanks for helping us get the details right 🙌

   _Generated by make-it-work, an AI workflow by InsideOut AI. Your answers guide the final requirements._
   ```

   - Keep the ticket-identifying first line exactly as shown; Phase 5C uses the recorded first line to find the sent message.
   - Use the real ticket URL from Phase 1. If none can be resolved, use the ticket ID/title as plain text and tell the user the link was unavailable when showing the message; never invent a ticket URL.
   - Number each question as in the questions file, with its options lettered `A`, `B`, `C`…, `(Recommended)` kept on the recommended option, and every conditional question marked `(answer only if Q<n> = <letter>)`. Omit the Skip option and the `Other:` line — the PM can always reply in free text.
   - Keep the AI disclosure visible as a short italic footer. Describe the questions as details to clarify rather than "gaps," and avoid promising how little time answering will take.
4. **Save before delivery.** Write the questions file to `make-it-work/<TICKET-or-slug>/<TICKET-or-slug>-questions.md` using the Phase 5B template (preserving answers and deferred-question notes for a Phase 5E handoff), plus a `### Slack` block at the end of `## Session Context`:

   ```markdown
   ### Slack

   - Product Manager: <display name> (<Slack user ID>)
   - Direct message: <DM channel ID>
   - Delivery mode: <draft | send>
   - Delivery status: prepared
   - Prepared at: <ISO 8601 UTC timestamp>
   - First line: close-the-gaps — <TICKET-or-slug>: <ticket summary>

   #### Message

   <the exact composed message>
   ```

   Keep the file `Awaiting Answers` and its checkboxes available for manual answers. Until delivery resolves, replace the template's "Fill in the checkboxes…" status note with "Questions prepared for `<PM name>` in Slack; delivery pending." If saving fails, stop before any delivery call.
5. **Deliver once in the selected mode.**
   - **Draft:** create a draft direct message in the user's own Slack. Never call a send tool. On success, set `Delivery status: draft`, record `Draft created: <UTC timestamp>`, and update the status note to "Questions drafted to `<PM name>` in Slack. Send the draft, then re-invoke `/make-it-work:close-the-gaps <this file's path>` once they reply in the Slack thread. Resuming reads their answers directly from Slack and continues refinement."
   - **Send:** persist `Delivery status: pending` immediately before the send call, then send the displayed message to the confirmed PM. On confirmed success, set `Delivery status: sent` and record `Sent at`, the returned `Message timestamp`/ID, and `Message link` when available. Update the status note to "Questions sent to `<PM name>` in Slack. Re-invoke `/make-it-work:close-the-gaps <this file's path>` once they reply in the Slack thread. Resuming reads their answers directly from Slack and continues refinement." A mode or recipient change from the user before delivery takes precedence over the initial choice.
   - **Interruption or uncertain result:** a timeout or missing acknowledgement does not prove failure. Keep `Delivery status: unknown` (or the already-saved `pending` if interrupted). Reconcile read-only in the recorded DM using the sender, timestamp, and exact stored message before any retry. If found, record its ID and mark it `sent`. Otherwise report delivery as unconfirmed and stop without sending again or creating a fallback draft. Resume through Phase 5C; a retry requires a new explicit user instruction after reconciliation.
6. **Report the actual result and stop.** For a standalone draft: "A draft direct message to `<PM name>` is waiting in your Slack. Review and send it. Once they reply in the Slack thread, run `/make-it-work:close-the-gaps <path>`. That reads their answers directly from Slack and continues refinement toward the final Gherkin spec. The workflow is paused; no Slack polling is running. No spec has been written yet." For a standalone confirmed send: "Sent to `<PM name>` ✅" with the returned message link when available, then "The workflow is paused pending their Slack replies; no polling is running. Once `<PM name>` replies in the Slack thread, run `/make-it-work:close-the-gaps <path>`. That reads their answers directly from Slack and continues refinement toward the final Gherkin spec. No spec has been written yet." When run by `implement`, use the return report in **When run by implement** instead; the orchestrator supplies its own resume instructions. For unconfirmed delivery, say so plainly and give the saved file path. Do not proceed to Phase 6 in this session. Do not claim a message was sent based only on its selected mode.

**If Slack can't be used** — no integration, no matching PM, or a definite delivery failure — explain exactly what failed. For send mode, if sending is unavailable or definitively failed and draft creation is supported, create a draft instead and record/report that fallback as draft-only. If no draft can be created, follow Phase 5B with the questions already built (no `### Slack` block). Report the offline handoff explicitly: "Slack delivery wasn't completed: <reason>. Forward or attach `<questions-file-path>` to the Product Manager manually. Once they've filled in the answers, re-invoke `/make-it-work:close-the-gaps <questions-file-path>`." These fallbacks apply only when no message could have been sent; never discard pending/unknown delivery metadata.
