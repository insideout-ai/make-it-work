## Final approval (new runs only)

After Final context sync, runs with `final_package_version: 1` checkpoint `phase: final-approval` and follow the Final approval package section below. Older runs proceed directly to Completion.

## Final approval package

This section applies only when the state has `final_package_version: 1`. It never commits, pushes, or opens a PR. The local helper is `<base>/scripts/final-package.mjs`.

1. Resolve the exact affected repo roots from every `## Affected Code` section, including `(test scope only)` sections with that suffix stripped, and the workspace service map. Find each `<repo>` root the way `execute` finds a Tests line's repo root. Leave out a test-scope repo with no changed paths (`git -C <repo> status --porcelain -- . ':!make-it-work'` is empty): do not branch it or pass its `--repo`, and say so in the package summary. Each repo's base follows the Base branch rule in that repo. For one repo, use its git root. For more than one, pass each root explicitly; pass its base branch with a paired `--base` when the state's `base` does not apply to every repo. Do not add unrelated repos. If a repo or base is ambiguous, ask the developer (Autopilot: stop). In Lightweight mode there is no Affected Code: take the repo roots from the Lightweight report's `## Changed paths`, confirmed against each repo's `git status`.
2. Write `make-it-work/<TICKET>/<TICKET>-final-draft.json` with `commit_message`, `pr_title`, and `pr_description`. Draft text summarizes the implemented behavior, acceptance-criteria coverage, validation, and notes for reviewers. These commit/PR drafts remain local; authorized ticket updates follow their separate publication policy. Keep secrets out.
   For each remaining test-scope repo still on its base branch, apply the Branch guard rules (Start check 4) to that repo: the suggested name computed in that repo (`git -C <repo> rev-parse --verify --quiet refs/heads/<name>`), the same `AskUserQuestion` without **Proceed on `<base>` anyway** (Autopilot: create and switch, logged), using `git -C <repo> switch -c <name>`. **Stop** checkpoints `status: Stopped` in `final-approval`. Uncommitted test edits carry over to the new branch. This satisfies `deliver`'s non-base-branch check.
3. Run `node "<base>/scripts/final-package.mjs" build --root <artifact-root> --state <state-path> --draft <draft-path> --repo <repo-root> [--repo <other-root> ...] [--base <base-for-first-repo> --base <base-for-second-repo> ...]`. The helper writes `make-it-work/<TICKET>/<TICKET>-final-package.md`, its JSON manifest, and one binary-safe diff per repo. It returns the package SHA-256. If it fails, stop with its specific error and repair the source; never claim that a package exists when build failed.
4. Show the package path, changed paths, validation mode/result, review outcome, any known regressions or open nits, AC verification status when the ledger exists, and the full proposed commit and PR text. In Guided mode ask **Approve** / **Request changes** / **Stop**. Only an explicit Approve of this exact package hash permits `node "<base>/scripts/final-package.mjs" approve --root <artifact-root> --state <state-path> --hash <shown-hash>`. In Autonomous and Autopilot, create and verify the package without asking; changes remain local and uncommitted. When the gate failed only on failures triage classified as unrelated, the validation result says so; list each of those Known regressions by name in this approval, so approving the package is the recorded acceptance of them. A failed gate without that recorded triage cannot be packaged.
5. Immediately before Completion, run `final-package.mjs check --root <artifact-root> --state <state-path> --require-approval` for Guided, or omit `--require-approval` for Autonomous/Autopilot. A failed check prevents Completion. A changed draft or package presentation requires rebuilding the package and, in Guided, asking again. A changed code, test, documentation, spec, plan, or validation artifact requires rerunning the affected Execute validation/Review/Final context sync work before rebuilding. The previous approval file may stay as history, but its old hash no longer approves the new package.

On **Request changes**, save the developer's notes in `make-it-work/<TICKET>/<TICKET>-final-feedback.md`. Draft-text-only feedback updates the draft, rebuilds the package, and returns to this gate. For implementation or documentation feedback, feed that file to `plan-the-work` in amend mode through the existing Fix path, then Execute, Review, Final context sync, and build a new package; the existing fix and review limits apply. Feedback that changes the approach or requirements uses the existing Replan route and its limit. In Lightweight mode, implementation or documentation feedback goes through Lightweight fix instead of `plan-the-work`, then Review onward; feedback that changes the approach escalates — there is no stage handoff at this gate, so checkpoint the escalation directly with Escalation's side effects and `Escalation:` row, without calling `handoff.mjs next`. On **Stop**, checkpoint the reason and wait for a new invocation. Resume in `final-approval` must run the helper's `check` before accepting any saved approval.
