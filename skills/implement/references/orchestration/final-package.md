## Final approval (new runs only)

After Final context sync, runs with `final_package_version: 1` checkpoint `phase: final-approval` and follow the Final approval package section below. Older runs proceed directly to Completion.

## Final approval package

This section applies only when the state has `final_package_version: 1`. It never commits, pushes, or opens a PR. The local helper is `<base>/scripts/final-package.mjs`.

1. Resolve the exact affected repo roots from every `## Affected Code` section, including `(test scope only)` sections with that suffix stripped, and the workspace service map. Find each `<repo>` root the way `execute` finds a Tests line's repo root. Leave out a test-scope repo with no changed paths (`git -C <repo> status --porcelain -- . ':!make-it-work'` is empty): do not branch it or pass its `--repo`, and say so in the package summary. Each repo's base follows the Base branch rule in that repo. For one repo, use its git root. For more than one, pass each root explicitly; pass its base branch with a paired `--base` when the state's `base` does not apply to every repo. Do not add unrelated repos. If a repo or base is ambiguous, ask the developer (Autopilot: stop). In Lightweight mode there is no Affected Code: take the repo roots from the Lightweight report's `## Changed paths`, confirmed against each repo's `git status`.
2. Prepare delivery prose as data. Allocate three inputs with `node "<base>/../../scripts/artifact-output.mjs" allocate --root <artifact-root> --directory make-it-work/<TICKET> --name <role>.txt`, using roles `commit-message`, `pr-title`, and `pr-description`. Write text to each returned absolute `file` using Write/Edit; never interpolate prose into shell commands, heredocs, or executable code. Summarize implemented behavior, acceptance-criteria coverage, validation, and reviewer notes; keep secrets out.

   Run `node "<base>/scripts/final-package.mjs" draft --root <artifact-root> --state <state-path> --commit-file <returned-commit-file> --title-file <returned-title-file> --description-file <returned-description-file>`. If inspected repository conventions give an explicit commit-body line limit, add `--body-width <limit>` (the strictest applicable known limit for shared text). The helper reads literal prose, serializes the existing three JSON keys, and returns the canonical draft `file`; use it as `<draft-path>` below. Without a known limit it preserves commit text. With a limit it wraps body prose, preserving the subject, fenced/indented code, trailers and long unsplittable tokens; inspect returned `overlong_commit_lines` and resolve actual convention conflicts before approval. It does not execute repository hooks/configuration or promise hook success. Read the resulting draft before building. Formatting occurs here, never during delivery of approved text. Existing JSON drafts/build/check/approve calls remain supported. Draft-only revisions use the same preparation command and existing rebuild/reapproval flow. These drafts remain local; ticket publication follows its separate policy.
   For each remaining test-scope repo still on its base branch, apply the Branch guard rules (Start check 4) to that repo: the suggested name computed in that repo (`git -C <repo> rev-parse --verify --quiet refs/heads/<name>`), the same `AskUserQuestion` without **Proceed on `<base>` anyway** (Autopilot: create and switch, logged), using `git -C <repo> switch -c <name>`. **Stop** checkpoints `status: Stopped` in `final-approval`. Uncommitted test edits carry over to the new branch. This satisfies `deliver`'s non-base-branch check.
3. Before constructing the package, if `change_assessment_version: 1`, invoke `/make-it-work:assess-change` with the ticket, artifact root, and the exact repo/base set resolved above. This applies to both Lightweight and TDD after final context sync. Use its matching-snapshot reuse path on resume; reassess changed snapshots. Assessment is informational: never change the implementation mode, approvals, review verdict, regression gate or CI/CD based on its ratings or failure. If assessment fails, use the skill's `fail` command with the concrete reason; continue packaging with **Assessment unavailable** and stale history only. Missing reports are likewise disclosed as unavailable by the package helper. Older runs without this marker skip automatic assessment; explicit requests produce separate reports under a fresh assessment identifier and preserve existing packages/approvals.

   Before invoking the assessment, checkpoint its activity using `node "<base>/scripts/dashboard-checkpoint.mjs" activity --state <state-path> --activity "Assessing code complexity and production risk" --category investigation/setup`. After the result, failure or matching-report reuse returns, checkpoint `--activity "Preparing final review"` before building the package. These are activities within the existing Finalizing phase, not new stages. Finalizing elapsed time includes the assessment interval, final review and session feedback; do not add the assessment interval again.

   Run `node "<base>/scripts/final-package.mjs" build --root <artifact-root> --state <state-path> --draft <draft-path> --repo <repo-root> [--repo <other-root> ...] [--base <base-for-first-repo> --base <base-for-second-repo> ...]`. The helper writes `make-it-work/<TICKET>/<TICKET>-final-package.md`, its JSON manifest, and one binary-safe diff per repo. It returns the package SHA-256. If it fails, stop with its specific error and repair the source; never claim that a package exists when build failed.
4. Show the change assessment summary, completeness, deciding rationale and report links (or unavailable reason and clearly stale history), then the package path, changed paths, validation mode/result, review outcome, any known regressions or open nits, AC verification status when the ledger exists, and the full proposed commit and PR text. The dashboard presents assessment only in final-approval/completion header badges on a second row below the workflow settings and in the persisted audit log; do not add an assessment section or timeline stage. Saving the result or rendering the final dashboard checkpoints the linked audit entry, including the rationale, with existing deduplication. Earlier phases hide the badges, stale/unavailable evidence gets a neutral badge, and reports/package retain the details. In Guided mode ask **Approve** / **Request changes** / **Stop**. Only an explicit Approve of this exact package hash permits `node "<base>/scripts/final-package.mjs" approve --root <artifact-root> --state <state-path> --hash <shown-hash>`. In Autonomous and Autopilot, create and verify the package without asking; changes remain local and uncommitted. When the gate failed only on failures triage classified as unrelated, the validation result says so; list each of those Known regressions by name in this approval, so approving the package is the recorded acceptance of them. A failed gate without that recorded triage cannot be packaged.
5. Immediately before Completion, run `final-package.mjs check --root <artifact-root> --state <state-path> --require-approval` for Guided, or omit `--require-approval` for Autonomous/Autopilot. A failed check prevents Completion. A changed draft or package presentation requires rebuilding the package and, in Guided, asking again. A changed code, test, documentation, spec, plan, or validation artifact requires rerunning the affected Execute validation/Review/Final context sync work before rebuilding. The previous approval file may stay as history, but its old hash no longer approves the new package.

For step 4, copy the built package's complete commit message, PR title and PR description verbatim into the approval message, using a separate text block for each. Include every paragraph and qualification so the developer can approve the exact proposed text in chat.

On **Request changes**, save the developer's notes in `make-it-work/<TICKET>/<TICKET>-final-feedback.md`. Draft-text-only feedback updates the draft, rebuilds the package, and returns to this gate. For implementation or documentation feedback, feed that file to `plan-the-work` in amend mode through the existing Fix path, then Execute, Review, Final context sync, and build a new package; the existing fix and review limits apply. Feedback that changes the approach or requirements uses the existing Replan route and its limit. In Lightweight mode, implementation or documentation feedback goes through Lightweight fix instead of `plan-the-work`, then Review onward; feedback that changes the approach escalates — there is no stage handoff at this gate, so checkpoint the escalation directly with Escalation's side effects and `Escalation:` row, without calling `handoff.mjs next`. On **Stop**, checkpoint the reason and wait for a new invocation. Resume in `final-approval` must run the helper's `check` before accepting any saved approval.

When presenting exact-package approval, preserve the checker’s assurance and every `validation_notes` qualification, distinguishing confirmed baseline evidence from attribution by inspection. Never upgrade suspected baseline errors to proven pre-existing errors or an unobserved scenario to passing coverage. User acceptance of Limited assurance does not change these facts.

For a newly prepared review target with `command_facts`, the package verifies and binds those records and raw-output hashes and preserves their generated qualifications in `validation_notes`. Include those notes in approval and completion without requiring a supplemental failed command to pass. The private package links exact capture records; safe generated qualifications flow to delivery preview without raw arguments or logs. Changed bound evidence requires the existing review/rebuild/reapproval route, not rerunning a command merely to recreate reporting. Saved packages/targets without this optional evidence retain their original behavior.

Apply [compilation evidence and branch provenance](../compilation-evidence.md): a ticket-scoped fix can coexist with an inherited failing branch build; starting-branch evidence does not prove destination provenance. Keep actual compiler status, full-output locators, failed startup and runtime-only JavaScript passes distinct in the existing qualifications through approval and delivery.
