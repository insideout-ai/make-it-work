# Assess complexity and production change risk

This is an informational assessment. It never changes implementation routes, validation requirements, review verdicts, approvals, or CI/CD behavior. Use `<plugin-root>/scripts/change-assessment.mjs` for snapshot capture, rating aggregation and reports. Read [the evidence contract](../../docs/change-assessment.md) before producing evidence.

## Resolve scope

- Implement-owned: use the controller's exact artifact root, ticket, approved repositories and base refs after final context sync. Run automatically only for `change_assessment_version: 1`, in both Lightweight and TDD. Older resumable runs retain their saved behavior.
- Standalone: require an explicit delivery, repository/base change scope, or PR reference. Ask for clarification before assessing ambiguous scope, including under Autopilot. Do not infer a delivery from whichever repository happens to be open.
- PR: use an available authenticated GitHub tool or `gh` to resolve repository, PR number, base and head SHAs. Inspect the full diff and relevant source/dependencies at that head, preferably in a disposable worktree on a temporary branch; do not change the user's checkout. Include the PR URL and fetched base/head SHAs in `reference`, and use the PR merge base as the explicit base. The snapshot's HEAD must equal the resolved PR head. If access fails, state the concrete limitation and that the PR was **not assessed**; save an unavailable report identifying the requested PR when possible. Never substitute a local checkout or truncated API diff for inaccessible PR content.
- Explicit assessment of an older run or completed delivery: create a fresh identifier such as `<TICKET>-assessment-<timestamp>`; do not edit its state, dashboard, package, approval, or original artifacts. Without a ticket use `assessment-<timestamp>`. Report paths remain clearly associated with `scope.label` and `reference`.

Write a scope JSON: `{ "label": "requested delivery description", "reference": "ticket/PR URL or explicit scope", "repos": [{ "path": "/absolute/repo", "base": "explicit-base-ref-or-SHA" }] }`. Include every relevant repository, even inaccessible ones. For an inaccessible PR use an unavailable repository path with the requested reference; use `fail`, never `write`.

## Gather and assess

1. Run `node <plugin-root>/scripts/change-assessment.mjs check --root <artifact-root> --ticket <identifier>`. Reuse only a current report matching the full requested scope (label, reference, repo/base set), rubric and snapshot. An unavailable report is not a successful reuse. A different requested scope needs fresh capture.
2. Run `... snapshot --scope <scope.json>`, saving the returned snapshot outside delivery source (under the assessment artifacts). It includes merge base, HEAD, base SHA, branch, changed paths and a binary-safe full-diff hash, including staged, unstaged and untracked files across repos. Inspect that full diff plus resulting changed functions, original functions at merge base, relevant unchanged callers, shared components and state. No changed function may be omitted merely because the edit is small. A failed or incomplete caller/dependency search is not evidence that no callers exist: repair the search or disclose the unassessed dependency scope with `full_scope: false`. Generated/binary or inaccessible scope is unsupported unless its behavior/impact is actually assessable; disclose it and its effect. Unrelated complexity cannot determine the rating.

   For caller searches, prefer `rg -n -F -- '<symbol>' '<repo-root>'` and inspect the matches, distinguishing definitions from callers. Quote any file globs passed to search tools (for example `--glob '*.py'` or `--include='*.py'`) so the shell does not expand them. When using Bash, run the search in its own tool call before filtering output or running unrelated commands; retain its actual exit status and diagnostics. For a completed rg/grep command, 0 means matches and 1 means no matches. Shell startup/glob errors mean the search was not performed; a later successful pipeline command does not repair that error. Before `write`, ensure the saved `dependencies` evidence describes checks that actually succeeded, or discloses the remaining gap.
3. Use already available analyzers or existing repository analysis commands without installing dependencies. Retain command/output evidence and analyzer configuration/thresholds. Analyze resulting changed functions and compare with their merge-base versions, distinguishing inherited complexity from introduced complexity. Cyclomatic bands: 1–10 Low, 11–20 Medium, 21+ High (grouped Radon bands). Report measured cognitive complexity against the analyzer's configured threshold; an exceedance is High under this conservative rubric. Measurements supplement qualitative judgments about understandability, coupling and state. If applicable measurements are absent, mark them missing and completeness partial, while retaining supported qualitative ratings. With `measurements: missing`, leave `metrics` empty; retain manual counts or incomplete analyzer observations in qualitative evidence and `measurement_limitation`. The helper rejects numeric metrics paired with missing measurements. Confirmed non-executable scope has Low code complexity and inapplicable metrics; assess its production risk independently.
4. For each repository provide dimension-level judgments and exact file/symbol evidence using the contract. Code: Low straightforward/local logic; Medium interacting branches/dependencies/state; High deeply nested or indirect logic, tightly coupled state or complex concurrency. Risk: Low localized/compatible/easy rollback; Medium shared components/multiple flows/bounded operations; High sensitive security or financial behavior, destructive data changes, breaking contracts, broad impact or difficult rollback. Rate the **resulting** changed functions, including inherited complexity. Complexity sets a minimum risk; a tiny sensitive change may independently be High risk. Explain which dimension decides each rating. Missing evidence never defaults to Low.
5. Run `... write --root <artifact-root> --ticket <identifier> --scope <scope.json> --input <evidence.json>`. This recaptures the snapshot and rejects stale evidence. If the snapshot changed, inspect the changed scope and retry with fresh evidence. The helper computes completeness and overall ratings; unsupported scope yields Unknown (`null`) delivery ratings while retaining assessed portions. Full relevant scope plus all applicable measurements is complete; useful assessment with missing scope/measurements is partial; no usable assessment is unavailable.
6. On assessment failure run `... fail --root <artifact-root> --ticket <identifier> --scope <scope.json> --reason "actual failure"`. This replaces current presentation with Assessment unavailable and retains prior reports only as linked stale history. If saving also fails, disclose that limitation and let Implement continue with unavailable information. Never use previous ratings as current. Regenerate the Implement dashboard after writing, using its existing render-status command.

Return both ratings, completeness, deciding rationale, limitations, exact revision/snapshot, and links to `<identifier>-complexity.md` and `.json`. Before reporting success, use `check` to confirm the reports match the current snapshot. Standalone output is separate from existing workflow packages. Do not rewrite completed packages.
