# Optional Jira creation

Read this reference only for interactive Jira creation after the overview and all individual slice files have been saved. Autopilot never offers or performs this step. Prefer the available Jira connector; do not assume a particular organization, issue type ID, custom field name, or parent convention.

## Prepare a concrete offer

Use the source Epic's destination project when established and appropriate. Otherwise ask which Jira site/project to use if it is not already known. Discover the project's available issue types, create permissions, and creation metadata for each proposed type, including all pages of required fields and allowed values. Tool presence alone is not proof of authentication or create access. If the integration cannot discover a required configuration or cannot create the proposed tickets, explain the limitation and retain the local deliverables; do not invent values or substitute unrelated destinations.

Present a compact proposal: `Slice | Title | Proposed type | Destination project | Proposed parent`. Propose Story for user-facing slices and Task for technical tasks and research spikes. Let the user adjust these choices before creation. Resolve the actual supported type IDs using the destination's metadata. If Story or Task is unavailable, ask the user to choose an available alternative rather than silently substituting a type.

Include native Jira dependency links in the same offer: list each planned hard edge as `S-A blocks S-B` and show the unique edge count. Derive the count from the actual dependency map; never assume a fixed count or a linear chain. Explain that approval covers creating these links after the slice tickets exist. Recommended sequencing remains informational and is not included as blocking links. Discover link capabilities and the destination's available blocking relationship; disclose unavailable linking without silently substituting another relationship type.

If the requirement came from a Jira Epic, offer to create the tickets as **children of that same Epic**, naming and linking it. Explain that approving creation under this source also includes posting the **entire overview, with its diagram converted to readable plain text**, as a comment there after the ticket and link attempts. Only apply parenting if the user selects it, and verify that the destination/type supports that relationship. Epic children are normal Stories/Tasks, not subtasks. Use the integration's supported parent relationship, not a generic issue link; do not hard-code an organization's Epic field. If the requested relationship cannot be set, ask how to proceed before creating an affected ticket. A source issue that is not an Epic does not imply an Epic parent. Do not create a new Epic as part of this offer.

Ask whether to create the proposed tickets and hard-dependency links, allowing the user to adjust the proposal or decline. Use an available question tool, or ask in chat and wait. Saving files, providing a Jira URL, or silence is not consent. Honor existing authorization for each action: an explicit request to add the hard-dependency links is sufficient, and an approval of the disclosed ticket/link offer needs no further permission round. If prior consent expressly covered ticket creation only, present just the missing link scope and count before requesting that additional authorization; do not repeat the ticket-creation question. Explicit approval to create children under the supplied source ticket also covers the full-overview comment described below. Respect explicit exclusions for linking or commenting. These approvals do not authorize editing the source Epic's description or unrelated tickets/links.

## Resolve mandatory information

Check mandatory fields for each selected project/type, including organization-specific fields, accepted formats, and allowed values. Reuse values already supplied for these tickets or applicable defaults explicitly provided by the destination's configuration. Do not copy arbitrary values from the source Epic or infer business choices merely to satisfy validation.

For missing or invalid values, ask the user what to use, naming fields in business terms and offering the valid choices when available. Show which slices the question affects and allow a common value where appropriate. Ask only about unresolved information, not values already established. If the user defers a value, mark affected slices pending and keep their files. Do not create affected tickets until all required values are valid. Continue with unaffected, authorized slices.

Recheck required information after a user changes a project or issue type. If Jira reveals an additional requirement or rejects a supplied value during creation, ask for the necessary correction before attempting that slice again. Collecting a missing value does not require another creation-approval round within the agreed scope.

## Create and track results

Create one issue per agreed slice. Preserve the complete story or technical objective, acceptance criteria or completion evidence, stable slice ID, and prerequisite information in the destination's supported description format. A local Markdown path is not a substitute for the slice content. Set the agreed type, project, required values, and parent Epic when chosen. Then create the authorized native dependency links as described below; describing a prerequisite alone does not create a Jira link.

Record results as they arrive in a **Jira creation results** section of the current overview, with a corresponding ticket reference in each successfully created slice file. Use a table such as `Slice | Title | Type | Status | Ticket | Parent Epic | Detail`. Include confirmed issue keys and clickable ticket links; keep failed, pending, and uncertain results distinct. Updating these current-run records is part of completing the output and does not authorize overwriting earlier backlog versions. If a local result-record write fails, report it and preserve the confirmed results in chat; do not repeat a remote creation to repair local recording.

Continue with unaffected slices after a creation failure. Report the failure and do not retry that slice until the user requests it. On an authorized retry, consult the saved results, skip confirmed successes, and retry only the requested unresolved slices. Read prior creation records when resuming or refining a backlog; a new Markdown version is not a reason to create another set of existing tickets.

If a request times out or its response is lost, mark the result **uncertain**, not failed or created. Before any requested retry, reconcile against Jira and the saved slice context to establish whether the ticket already exists. Reuse a confirmed existing ticket; if the outcome cannot be established, leave it uncertain and explain why another creation cannot safely proceed. Never assume that no response means no ticket was created.

## Create native hard-dependency links

For each approved hard edge `S-A -> S-B`, resolve both stable slice IDs to their confirmed Jira issue keys and create **A blocks B**, which must appear reciprocally as **B is blocked by A**. Use the connector's documented direction and the destination's discovered blocking type rather than guessing from inward/outward parameter names. Create one relationship per unique direct hard edge from the plan; do not add reverse duplicates, inferred transitive edges, recommended-order links, or links to external/unapproved tickets.

Before creating an edge, inspect existing issue links and reuse an identical link with the same type and direction. Both endpoint tickets must be confirmed; mark an edge pending when either slice failed, is pending, or has an uncertain issue key. Continue with independent linkable pairs. If the blocking type, permission, or connector capability is unavailable, report affected edges as unavailable/pending rather than replacing them with a generic link. Avoid additional per-issue comments when the link tool offers that optional behavior.

Read back the endpoints to verify that the predecessor blocks the successor, then record a **Jira dependency link results** table in the current overview: `Predecessor | Successor | Jira blocker | Jira blocked | Status | Link ID | Detail`. Distinguish created, already present, failed, pending, and uncertain results. A request receipt without direction verification is not evidence of a fully verified dependency. Link failure does not undo or duplicate successful ticket creation, or prevent the authorized overview comment.

Do not automatically retry a failed or uncertain link. On a user-requested retry, inspect saved results and current Jira links first, skip confirmed existing relationships, and reconcile uncertain outcomes before another create call. If the outcome remains unknown, leave it uncertain. Do not recreate tickets to repair links or delete/reverse other relationships as part of adding the approved edges. Record receipts in chat if saving local results fails; do not repeat the remote operation to repair local recording.

## Comment the entire overview on the source ticket

Post this comment only when the user has explicitly authorized creating slice tickets **as children of the supplied original Jira ticket**, and that original ticket is the agreed parent. The presence of a source reference, completed local slices, approval to slice, or permission to create issues elsewhere does not meet this condition. Skip commenting when the user declines creation, leaves authorization or parenting unresolved, requests no comment, or runs in autopilot. Use the resolved source ticket and site; do not substitute a related issue or a newly created child.

After the authorized ticket and link attempts finish, synchronize the overview's **Jira creation results** and **Jira dependency link results** with confirmed outcomes. Then read the **entire latest saved overview Markdown** and use that document as the comment body, converting only its diagram and unsupported formatting for readability. Include every section and its full content: epic goal and source, selected approach and rationale, assumptions and open questions, the complete Slice summary table, **the full dependency diagram represented as a plain-text list and legend**, the relationship table, recommended implementation stages and parallel opportunities, MVP boundary, creation/link results, and any additional sections present. These are examples of required content, not a whitelist for discarding other sections. Posting does not require all ticket or link attempts to succeed; an issue whose parenting failed must not be represented as a confirmed child.

Keep the original Mermaid diagram in the local overview. In the Jira comment, **replace its Mermaid code block with a readable plain-text dependency list**, using stable IDs, titles, and confirmed Jira keys/links where available. For example, write `S-1 (KEY-1) -> S-2 (KEY-2): planned hard prerequisite`. Show recommended edges separately as `recommended only, not a blocker`, and list independent slices explicitly. Preserve every node and every edge, including multiple prerequisites and shared successors; a tree must not hide a second parent. Format the Jira diagram as ordinary text/list content; keep raw Mermaid syntax in the local file. This conversion needs no rendering plugin or image-generation tool. Explain that this list is a snapshot of the plan; native issue links are stored relationships and the comment is refreshed only when this workflow runs again.

Preserve all other overview content when adapting formatting. Use real Jira links for confirmed tickets in place of local slice links; for slices without a Jira ticket, preserve the stable ID, label, and filename as readable text, for example `S-2 (slices-example-S-2-title.md)`. Include any existing **Jira summary comment** section and its pre-send status in this snapshot; do not drop it as internal bookkeeping. Keep intended hard dependencies visible in the diagram even when native link creation failed or is pending, and use the link-results table to distinguish the plan from confirmed Jira relationships. Do not replace the full overview with an attachment or a short summary. If a destination limit prevents publishing the complete document, report the limitation and retain the complete local file rather than presenting a partial comment as complete.

Before sending, compare the prepared comment against the saved overview snapshot to ensure all sections, rows, diagram content, and implementation stages survived the formatting and link changes. After posting, read back the comment and verify that the complete content, especially the diagram and relationship table, is present; report an unverified or incomplete publication accurately. The separate autopilot JSONL audit file is outside the overview and is not appended automatically.

Record the source ticket, comment status, confirmed comment ID/link when available, and any error or uncertainty in a **Jira summary comment** section of the current overview. Report the comment result separately from issue creation; missing comment capability or a failed comment does not invalidate the created tickets or local files. Claim success only from a confirmed connector result. Never recreate tickets because commenting failed.

The published content is the overview snapshot prepared before the send. Recording the returned comment ID/link afterward is a local receipt update; do not repost merely to include the comment's own receipt in its body.

On resume or a user-requested retry, consult the saved comment record. Reuse a confirmed comment and update that same run's comment when refreshing results or replacing its earlier Mermaid block with the plain-text list, if editing is supported. If the user supplies an existing comment ID, resolve it against the original source ticket and verify it is the intended workflow comment before editing; never hard-code an example comment ID. Preserve all its other overview content. Do not append duplicate summaries or edit another person's unrelated comment. If an update is unsupported, report the pending refresh instead of silently adding another comment. If a comment request times out or its response is lost, mark it uncertain and reconcile against the source ticket before any requested retry. If its existence cannot be established, leave it uncertain rather than posting again. Report failed or uncertain comments without automatically retrying them. If the local result-record write fails, preserve the confirmed comment ID/link in chat and do not repost to repair local recording.

## Report completion

Always return the complete list of confirmed created tickets in chat: slice ID, ticket key, title, issue type, clickable link, and parent Epic when used. Report failed slices with reasons, pending slices with missing information, and uncertain results separately, so partial success is clear. Link the saved overview and keep it consistent with the report. Do not claim a ticket or parent relationship was created without confirmation; if creation succeeds but parenting fails, report the existing ticket and the unresolved relationship rather than creating it again.

Also report whether the source summary comment was posted, failed, uncertain, or skipped, including its link when confirmed and available. A prepared local comment is not a posted comment.

Report the number of native hard-dependency links created and already present, and list failed, pending, or uncertain edges by slice IDs and known ticket keys. Keep these outcomes separate from ticket creation and source-comment status.

If creation is declined or no usable creation integration is available, return the local file links and explicitly report both `Jira tickets: not created — <reason>` and `Source overview comment: skipped — <reason>`. Do not omit the comment status just because no remote action occurred. Missing Jira access must not invalidate or withhold the completed local backlog.
